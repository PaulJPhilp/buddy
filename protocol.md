# WebSocket Protocol for Buddy Chat Application

## 1. Overview

This document defines the WebSocket communication protocol used by the Buddy chat application. The protocol enables real-time, bidirectional communication between clients (e.g., web browsers, mobile apps) and the chat server/agent runtime. It facilitates the exchange of user messages, LLM responses, system status updates, and more.

All messages exchanged over WebSocket are JSON-encoded objects. This document details the structure and purpose of each message type.

## 2. Base Message Structure

All messages, whether client-to-server or server-to-client, inherit from a `BaseMessage` interface.

```typescript
export interface BaseMessage {
    /** 
     * Timestamp of when the message was created, in ISO 8601 format.
     * Example: "2023-10-26T07:46:36.611Z"
     */
    readonly timestamp: string;

    /** 
     * Optional unique message ID. 
     * If not provided by the sender for client messages, it might be generated by factories.
     * Server messages typically include an ID.
     * Example: "b7zfsTOpX0f7vN5bX2Yt0" (generated by nanoid)
     */
    readonly id?: string;
}
```

## 3. Client-to-Server Messages

These are messages sent from the client to the server.

### 3.1. `UserMessage`

Sent when the user submits a message in the chat.

```typescript
export interface UserMessage extends BaseMessage {
    readonly type: "USER_MESSAGE";
    readonly text: string; // User's message content, trimmed.
    readonly metadata?: {
        readonly userId?: string;
        readonly sessionId?: string;
        readonly attachments?: readonly string[]; // URLs or identifiers for attachments
        readonly chatId?: string; // Identifier for the specific chat session
    };
}
```

**Example:**
```json
{
  "type": "USER_MESSAGE",
  "id": "usrMsg_123abc",
  "timestamp": "2024-07-30T10:00:00.000Z",
  "text": "Hello, how are you?",
  "metadata": {
    "userId": "user_johndoe",
    "sessionId": "session_xyz789",
    "chatId": "chat_agent_buddy_1"
  }
}
```

### 3.2. `ConnectionMessage`

Used for managing the WebSocket connection lifecycle, like connecting, disconnecting, or sending keep-alive pings.

```typescript
export interface ConnectionMessage extends BaseMessage {
    readonly type: "CONNECTION";
    readonly action: "CONNECT" | "DISCONNECT" | "PING";
    readonly connectionState?: ConnectionState; // Current or desired state by client
    readonly clientInfo?: {
        readonly userAgent?: string;
        readonly version?: string; // Client application version
    };
}
```
*(See Section 5 for `ConnectionState` details)*

**Example (Client sending a PING):**
```json
{
  "type": "CONNECTION",
  "id": "conn_ping_456",
  "timestamp": "2024-07-30T10:05:00.000Z",
  "action": "PING"
}
```

**Example (Client initiating CONNECT):**
```json
{
  "type": "CONNECTION",
  "id": "conn_init_789",
  "timestamp": "2024-07-30T09:59:00.000Z",
  "action": "CONNECT",
  "clientInfo": {
    "userAgent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/91.0.4472.124 Safari/537.36",
    "version": "1.2.3"
  }
}
```

## 4. Server-to-Client Messages

These are messages sent from the server to the client.

### 4.1. `AcknowledgmentMessage` (`ACK`)

Confirms receipt or status of a client message.

```typescript
export interface AcknowledgmentMessage extends BaseMessage {
    readonly type: "ACK";
    readonly originalMessageId?: string; // ID of the client message being acknowledged
    readonly status: "RECEIVED" | "PROCESSING" | "COMPLETED" | "ERROR";
    readonly message?: string; // Optional descriptive message
}
```

**Example:**
```json
{
  "type": "ACK",
  "id": "ack_abc789",
  "timestamp": "2024-07-30T10:00:01.000Z",
  "originalMessageId": "usrMsg_123abc",
  "status": "RECEIVED",
  "message": "User message received by server."
}
```

### 4.2. `LLMResponseMessage`

A complete response from the Language Model.

```typescript
export interface LLMResponseMessage extends BaseMessage {
    readonly type: "LLM_RESPONSE";
    readonly content: string; // The LLM's response text (can be Markdown)
    readonly finishReason?: string; // Reason why the LLM finished generating (e.g., "stop", "length")
    readonly metadata?: {
        readonly model?: string; // Identifier of the LLM used
        readonly usage?: {
            readonly promptTokens?: number;
            readonly completionTokens?: number;
            readonly totalTokens?: number;
        };
        readonly processingTime?: number; // Time in milliseconds for the LLM to generate the response
    };
}
```

**Example:**
```json
{
  "type": "LLM_RESPONSE",
  "id": "llm_resp_def456",
  "timestamp": "2024-07-30T10:00:05.000Z",
  "content": "I'm doing well, thank you for asking! How can I help you today?",
  "finishReason": "stop",
  "metadata": {
    "model": "gpt-4o",
    "usage": {
      "promptTokens": 15,
      "completionTokens": 25,
      "totalTokens": 40
    },
    "processingTime": 1500
  }
}
```

### 4.3. `LLMStreamMessage`

A chunk of a streaming response from the Language Model. This allows for displaying the response progressively.

```typescript
export interface LLMStreamMessage extends BaseMessage {
    readonly type: "LLM_STREAM";
    readonly content: string; // A portion of the LLM's response
    readonly isComplete: boolean; // True if this is the final chunk of the stream
    readonly streamId?: string; // Identifier for the entire stream, consistent across chunks
    readonly metadata?: {
        readonly model?: string;
        readonly chunkIndex?: number;
        readonly totalChunks?: number; // May not always be known
        readonly chatId?: string;
    };
}
```

**Example (Streaming chunk):**
```json
{
  "type": "LLM_STREAM",
  "id": "llm_stream_chunk_1",
  "timestamp": "2024-07-30T10:00:03.000Z",
  "content": "I'm doing well, ",
  "isComplete": false,
  "streamId": "stream_xyz123",
  "metadata": {
    "model": "gpt-4o",
    "chunkIndex": 0,
    "chatId": "chat_agent_buddy_1"
  }
}
```

**Example (Final streaming chunk):**
```json
{
  "type": "LLM_STREAM",
  "id": "llm_stream_chunk_final",
  "timestamp": "2024-07-30T10:00:05.500Z",
  "content": "How can I help you today?",
  "isComplete": true,
  "streamId": "stream_xyz123",
  "metadata": {
    "model": "gpt-4o",
    "chunkIndex": 2,
    "chatId": "chat_agent_buddy_1"
  }
}
```
*Note: `content` can be an empty string for a completion message if `isComplete` is true and all text has been sent in prior chunks.*

### 4.4. `ThinkingStateMessage`

Indicates that the agent is currently processing or "thinking".

```typescript
export interface ThinkingStateMessage extends BaseMessage {
    readonly type: "THINKING";
    readonly isThinking: boolean; // True if the agent started thinking, false if it stopped
    readonly message?: string; // Optional message, e.g., "Processing your request..."
}
```

**Example (Agent starts thinking):**
```json
{
  "type": "THINKING",
  "id": "think_start_789",
  "timestamp": "2024-07-30T10:00:01.500Z",
  "isThinking": true,
  "message": "Analyzing your query..."
}
```

### 4.5. `ErrorMessage`

Sent by the server when an error occurs.

```typescript
export interface ErrorMessage extends BaseMessage {
    readonly type: "ERROR";
    readonly code: string; // An error code (e.g., "VALIDATION_ERROR", "INTERNAL_SERVER_ERROR")
    readonly message: string; // A human-readable error message
    readonly details?: string; // Optional additional details about the error
    readonly recoverable?: boolean; // Whether the client might be able to recover or retry
}
```

**Example:**
```json
{
  "type": "ERROR",
  "id": "err_ghi789",
  "timestamp": "2024-07-30T10:00:02.000Z",
  "code": "RATE_LIMIT_EXCEEDED",
  "message": "You have sent too many messages. Please try again later.",
  "details": "Limit is 10 messages per minute.",
  "recoverable": true
}
```

### 4.6. `WelcomeMessage`

Sent by the server upon successful client connection, can include server information.

```typescript
export interface WelcomeMessage extends BaseMessage {
    readonly type: "WELCOME";
    readonly message: string; // Welcome message text
    readonly serverInfo?: {
        readonly version?: string; // Server application version
        readonly capabilities?: readonly string[]; // List of server capabilities
    };
}
```

**Example:**
```json
{
  "type": "WELCOME",
  "id": "welcome_jkl012",
  "timestamp": "2024-07-30T09:59:01.000Z",
  "message": "Welcome to Buddy Chat! You are now connected.",
  "serverInfo": {
    "version": "2.1.0",
    "capabilities": ["streaming", "attachments"]
  }
}
```

## 5. Connection States

The `ConnectionState` type defines the possible states of the WebSocket connection, primarily communicated by the server or reflected in client-side state management. The `useChatInstance.ts` hook, for example, uses these states to update the UI.

```typescript
export type ConnectionState =
    | "DISCONNECTED"
    | "CONNECTING"
    | "CONNECTED"
    | "RECONNECTING"
    | "ERROR"; // A persistent error state for the connection
```
The server might also send `CONNECTION` type messages (distinct from client `ConnectionMessage`) to inform the client about changes in its connection state from the server's perspective, as seen in `useChatInstance.ts` (e.g., a server-sent `CONNECTION` message with `connectionState: "RECONNECTING"`).

## 6. Message Flow (Simplified Example)

1.  **Client Connects**: Client establishes WebSocket connection.
2.  **Server Sends Welcome**: Server sends a `WelcomeMessage`.
3.  **Client Sends UserMessage**: User types and sends a message, client emits `UserMessage`.
4.  **Server Acknowledges**: Server may send an `AcknowledgmentMessage` (`status: "RECEIVED"`).
5.  **Server Sends Thinking (Optional)**: Server sends `ThinkingStateMessage` (`isThinking: true`).
6.  **Server Processes**: Agent processes the message.
7.  **Server Sends LLMResponse/LLMStream**:
    *   For streaming: Server sends one or more `LLMStreamMessage` chunks, ending with `isComplete: true`.
    *   For non-streaming: Server sends a single `LLMResponseMessage`.
8.  **Server Sends Thinking (Optional)**: Server sends `ThinkingStateMessage` (`isThinking: false`).
9.  **Server Acknowledges (Optional)**: Server may send an `AcknowledgmentMessage` (`status: "COMPLETED"`).

*(Error messages can be sent at various points if issues arise.)*

## 7. Error Handling

-   Server-side errors are communicated to the client using the `ErrorMessage` type.
-   These messages include an error `code`, a human-readable `message`, optional `details`, and a `recoverable` flag.
-   Clients should handle these errors gracefully, potentially displaying messages to the user or attempting recovery actions if `recoverable` is true.
-   Validation failures for incoming messages (e.g., malformed JSON, missing required fields) can also result in `ErrorMessage`s. The `validators.ts` file in `packages/protocol` defines rules for message validity.

## 8. Message Identification

-   The `id` field in `BaseMessage` is optional.
-   Client-side message factories (see `packages/protocol/src/factories.ts`) typically generate a unique `id` (e.g., using `nanoid`) if one is not provided.
-   Server messages will generally include an `id`.
-   The `AcknowledgmentMessage` uses `originalMessageId` to correlate with the client message it acknowledges. `LLMStreamMessage` uses `streamId` to group related chunks.

## 9. Connection Management

### 9.1. Reconnection
-   Clients are responsible for implementing reconnection logic (e.g., with exponential backoff) if the WebSocket connection is unexpectedly lost.
-   The server might inform the client of an impending or active reconnection attempt from its side via a `CONNECTION` message with `connectionState: "RECONNECTING"`.

### 9.2. Heartbeats / Keep-Alive
-   Clients can send `ConnectionMessage` with `action: "PING"` to the server.
-   The server is expected to handle these PING messages (e.g., by responding with a PONG or simply to keep the connection alive through intermediaries like load balancers). The `useChatInstance.ts` hook shows the client logging PINGs received *from the agent*, implying the agent might also send PINGs (as a `ConnectionMessage` with `action: "PING"`). The protocol should clarify if server-to-client PINGs are formally part of this spec or an agent-specific behavior. For now, client-to-server PING is defined.

## 10. Security Considerations

1.  **Authentication & Authorization**:
    *   Authentication should be handled at the WebSocket connection establishment phase (e.g., via secure tokens in query parameters or HTTP headers during the upgrade request). This protocol definition does not specify the auth mechanism itself.
    *   Authorization logic should be implemented server-side to ensure clients can only access permitted resources and actions.
2.  **Input Validation**:
    *   The server MUST validate all incoming messages against the defined schemas and business rules. The `packages/protocol/src/validators.ts` provides functions like `validateMessage` and `validateUserInput`.
    *   `sanitizeUserInput` is available in `validators.ts` to mitigate XSS risks if user-provided text is rendered directly as HTML (though rendering Markdown safely via a library is preferred).
3.  **TLS (Transport Layer Security)**:
    *   Always use WebSocket Secure (`wss://`) in production environments to encrypt communication and prevent eavesdropping or tampering.
4.  **Rate Limiting**:
    *   Implement server-side rate limiting to prevent abuse and ensure fair usage. Errors like `RATE_LIMIT_EXCEEDED` can be sent via `ErrorMessage`.

## 11. Versioning

The current protocol version is `2.0.0` (updated from the previous generic protocol). Any future breaking changes will result in a new version number. Non-breaking additions (e.g., new optional fields, new message types) may be introduced within the same major version.
