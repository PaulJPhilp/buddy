
**Product Requirements Document: Mock WebSocket Local Connection for Buddy <> EA**

**Version:** 0.1 (Draft)
**Date:** 5/4/2025
**Author:** Paul / T3 Chat

**1. Introduction**

This document outlines the requirements for establishing a **local, in-process communication bridge** between the "Buddy" ChatApp UI (React/Next.js) and the EffectiveAgent (EA) framework's runtime components (`AgentRuntimeService`, `AgentRuntimeInstance`) using a **mock WebSocket implementation**.

The primary goal is to enable **demos and testing** by allowing user input from the Buddy UI to trigger a specific chatbot agent hosted within the EA runtime and display the final response back in the Buddy UI, simulating the intended WebSocket communication pattern (Phase 4) but running entirely within a **single browser JavaScript process**.

This approach allows for the development and testing of the `WebSocketService` and the application's communication logic without requiring a separate backend server process during this phase.

**2. Goals**

*   Implement the core `WebSocketService` (Effect Service wrapping browser WebSocket API) as defined in the Phase 4 plan.
*   Utilize a mock WebSocket library (e.g., `mock-socket`) to intercept local WebSocket connections.
*   Implement mock server logic that runs in the same process to route messages between the mock WebSocket connection and the actual `AgentRuntimeService`.
*   Allow user messages entered in the Buddy ChatApp UI (sent via `WebSocketService`) to be routed as commands to a designated EA `AgentRuntime` instance.
*   Enable the Buddy ChatApp UI (receiving via `WebSocketService`) to display the final text response generated by the chatbot `AgentRuntime`.
*   Ensure the core chatbot logic execution and state management remain the responsibility of the EA `AgentRuntime` instance.
*   Provide a functional integration for demo and testing purposes that closely mirrors the final WebSocket architecture.

**3. Non-Goals (Out of Scope)**

*   Actual network communication or deployment of a real WebSocket server.
*   Complex error handling related to network conditions (focus on message routing logic).
*   UI for selecting different agents (target agent ID can be configured/derived).
*   Synchronization with any backend beyond the mock message passing.
*   Advanced WebSocket features (binary data, subprotocols unless strictly needed).

**4. Functional Requirements**

*   **`WebSocketService` Implementation:**
    *   An Effect service (`WebSocketService`) shall be implemented, providing methods like `connect(url)`, `disconnect()`, `send(data)`, and a `receive(): Stream<MessageEvent, WebSocketError>`.
    *   It should internally use the standard browser `WebSocket` API.
*   **Mock WebSocket Setup:**
    *   A mock WebSocket library (e.g., `mock-socket`) shall be integrated into the application's setup for demo/testing builds.
    *   This setup must intercept attempts by `WebSocketService` to connect to a predefined local mock URL (e.g., `ws://local-mock-ea-bridge`).
*   **Mock Server Logic:**
    *   Logic acting as the "server-side" of the mock WebSocket connection must be implemented within the same browser process.
    *   This logic must have access to the running `AgentRuntimeService` instance (via Effect context/layers).
    *   **Receiving from Client (Buddy via `WebSocketService`):**
        *   When the mock server receives a message (presumably a serialized `AgentActivity` representing user input) from the `WebSocketService`:
        *   It must deserialize the message.
        *   Determine the target `AgentRuntimeId` (e.g., from the message or use a configured default).
        *   Call `agentRuntimeService.send(targetId, deserializedActivity)`.
    *   **Sending to Client (Buddy via `WebSocketService`):**
        *   The mock server logic must subscribe to relevant activities from the target `AgentRuntime` instance(s) using `agentRuntimeService.subscribe(targetId)`.
        *   It should filter for activities representing the final response or significant events (e.g., `AGENT_RUN_COMPLETED`, `AGENT_RUN_FAILED`, or specific `CHAT_AGENT_RESPONSE` types).
        *   Upon receiving a relevant activity from the subscription, it must serialize the necessary information (e.g., the response payload).
        *   It must send the serialized data back over the mock WebSocket connection to the connected `WebSocketService`.
*   **Buddy UI Integration:**
    *   The Buddy ChatApp UI shall interact *only* with the `WebSocketService`.
    *   On user input, Buddy calls `webSocketService.send(...)` with the appropriate serialized `AgentActivity`.
    *   Buddy subscribes to the `webSocketService.receive()` stream to get responses.
    *   Buddy deserializes received messages and updates its `ChatState` to display the response.
*   **AgentRuntime Integration:**
    *   The `AgentRuntimeService` and `AgentRuntimeInstance` operate normally, unaware the communication is happening via a local mock socket.
    *   The `AgentRuntime` hosting the chatbot executes its `agentWorkflow` upon receiving the activity via `agentRuntimeService.send`.
    *   The `agentWorkflow` logs activities to the `AgentStore` as designed.

**5. Technical Design Notes**

*   **Serialization:** Define a clear serialization format (e.g., JSON) for `AgentActivity` objects sent over the mock WebSocket.
*   **Mock Server Implementation:** This could be a simple class or set of functions initialized during app setup that registers handlers with the `mock-socket` library. It needs access to the running Effect context to use `AgentRuntimeService`.
*   **Subscription Management:** The mock server logic needs to manage subscriptions to `AgentRuntimeService.subscribe` appropriately, potentially creating one subscription per connected mock client or per targeted `AgentRuntimeId`.
*   **Error Handling:** The mock server should handle errors during deserialization or when interacting with `AgentRuntimeService` and potentially send appropriate error messages back via the mock socket. The `WebSocketService` should surface connection/send/receive errors.
*   **Configuration:** The mock WebSocket URL and the target `AgentRuntimeId` should be configurable.

**6. Acceptance Criteria**

*   The `WebSocketService` can connect to the mock URL.
*   User input sent from Buddy via `WebSocketService.send` is received by the mock server logic.
*   The mock server logic successfully calls `AgentRuntimeService.send` with the correct `AgentActivity`.
*   The target `AgentRuntime` executes its workflow.
*   The mock server logic successfully subscribes to and receives the resulting `AgentActivity` (e.g., `AGENT_RUN_COMPLETED`) from the `AgentRuntimeService`.
*   The mock server logic successfully sends the relevant response data back over the mock socket.
*   The Buddy UI receives the response via `WebSocketService.receive()` and displays it correctly.
*   The entire flow occurs within a single browser process.
